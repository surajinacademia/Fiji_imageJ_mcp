# Fiji MCP v0.2.0 Local-First Universal Gateway Design

- **Date:** 2026-07-21
- **Status:** Conversational design approved; written-spec review pending
- **Target:** A breaking v0.2.0 release published from GitHub
- **Primary audience:** People who use Fiji through an AI assistant and should not need to write code or edit configuration files

## 1. Decision summary

Fiji MCP v0.2.0 will be a local-first product with three coordinated deliverables:

1. A **stdio MCP server** that exposes a small, stable tool surface and dynamically discovers the user's installed Fiji commands.
2. A **guided setup and diagnostic CLI** that installs and verifies the server for supported AI clients.
3. A **canonical agent skill** that teaches any compatible agent the same discovery, execution, verification, and safety workflow.

The MCP server is the capability boundary. The CLI makes it usable by non-coders. The skill improves agent behavior but is not required for correctness. There will be no standalone Fiji agent in v0.2.0 because that would duplicate the agent already supplied by Codex, Claude, ChatGPT, Cursor, or Copilot.

The runtime will use a coordinator process and a restartable Fiji worker process. This replaces the current in-process JVM lifecycle so a real timeout, cancellation, or Java failure cannot permanently kill the MCP connection.

This is intentionally a breaking release. Old tool names, schemas, environment behavior, and compatibility aliases will not be retained. The repository will advertise only features that have executable demos and adequate automated verification.

## 2. Context and reasons for replacement

The pre-v0.2 implementation has useful foundations—FastMCP over stdio, PyImageJ startup, image I/O, command discovery, an installer, and demo images—but its advertised surface is broader than its evidence.

The design audit found the following release-blocking problems:

- The repository exposes 19 MCP tools, while only four have any live-Fiji test coverage.
- The timeout wrapper does not interrupt a running Fiji operation because the operation executes inline.
- Generic retries can repeat a mutating operation and therefore duplicate side effects.
- Shared Fiji state is not serialized across operations.
- Automatic mode resolution can still call GUI display behavior after resolving to headless mode.
- The data-root policy covers selected path tools but does not contain arbitrary macros or scripts.
- Screenshot documentation and returned media formats disagree, and full-screen capture creates unnecessary privacy risk.
- Workflow verification checks screenshots rather than scientific results.
- Image-comparison helpers transform data before comparison and are unsuitable as scientific correctness oracles.
- Dynamic discovery exists, but generic execution does not yet cover the full discovered SciJava command catalog.
- Installer writes are insufficiently validated and are not consistently atomic or backed up.
- The existing tests do not enforce exact MCP schemas, annotations, coverage thresholds, static analysis, artifact contents, or all advertised client configurations.

On the Fiji installation used during the design audit, the catalog contained 2,073 commands. This number is installation-specific and is not a product constant. It demonstrates why v0.2 must discover the installed catalog dynamically instead of hard-coding thousands of individual MCP tools.

## 3. Product goals

### 3.1 Required outcomes

The release must let a non-coding user:

1. Run one copy-and-paste setup command.
2. Select or confirm their Fiji installation, approved data folders, safety profile, and AI clients through guided prompts.
3. Receive a clear diagnosis if Fiji, Java, Python, a client configuration, or an MCP handshake is not working.
4. Ask an AI assistant to find an installed Fiji capability, understand its parameters, run it, inspect the result, and save the result.
5. Use installed Fiji commands without waiting for a new MCP release for every plugin.
6. Understand when a command is unavailable because it needs a GUI, hardware, an update site, particular input data, or the trusted profile.
7. Recover the MCP connection after an operation timeout or worker crash.

### 3.2 Meaning of “all Fiji tools and features”

“All Fiji” is a gateway contract, not a promise to blindly execute every installed command during release testing.

The contract is:

- Enumerate the complete command catalog visible to the installed Fiji runtime.
- Give each discoverable command a stable identity within that Fiji installation.
- Return the exact metadata Fiji exposes for that command, including missing or incomplete metadata.
- Execute supported SciJava commands, Ops, installed script modules, and ImageJ1 plugins through generic executors.
- Offer trusted, opt-in macro and SciJava script execution for functionality that has no safe typed command interface.
- Scan and describe every installed catalog entry during verification.
- Execute scientifically checkable representatives from every supported capability family.
- Mark GUI-, hardware-, update-site-, external-service-, and input-dependent commands as conditional when their prerequisites are absent.
- Never label an unexecuted conditional command as scientifically verified.

This provides universal dynamic access while keeping the release testable and honest.

### 3.3 Non-goals

The following are explicitly outside v0.2.0:

- A web service, remote MCP transport, mobile application, or hosted data path.
- A standalone AI agent.
- A Fiji GUI plugin or a native graphical installer.
- Full-screen desktop capture.
- Automatic installation of Fiji plugins, update sites, models, or other packages by the AI agent.
- Backward-compatible aliases for pre-v0.2 tools or schemas.
- PyPI publication.
- New release-note documents.

Historical release artifacts and release notes remain untouched unless they are factually referenced by active documentation that must be corrected.

## 4. Users and primary experience

The primary user understands microscopy and Fiji, but may not understand Python, JSON, TOML, shells, MCP, or Java configuration.

The intended first-run experience is:

```text
copy one setup command
        |
        v
detect Fiji, Java, and supported AI clients
        |
        v
confirm data folders and standard/trusted profile
        |
        v
preview and atomically write selected client configurations
        |
        v
start the server and complete a real MCP/Fiji doctor check
        |
        v
show one plain-language example for the selected client
```

The stable GitHub release command will be documented in this form:

```bash
uvx --from git+https://github.com/surajinacademia/Fiji_imageJ_mcp.git@v0.2.0 fiji-mcp setup
```

During development and verification, the immutable commit SHA replaces `v0.2.0`. Setup may guide the user to install missing prerequisites, but it must not silently install Fiji, Java, AI clients, Fiji plugins, update sites, or models.

## 5. Runtime architecture

```text
Codex / ChatGPT / Claude / Cursor / Copilot
                    |
                    | local stdio MCP
                    v
          +-----------------------+
          | MCP coordinator       |
          | - schemas and policy  |
          | - operation queue     |
          | - audit history       |
          | - timeout/recovery    |
          +-----------+-----------+
                      |
                      | versioned framed messages
                      | over a private OS pipe
                      v
          +-----------------------+
          | Fiji worker process   |
          | - PyImageJ            |
          | - JVM/Fiji lifecycle  |
          | - catalog adapters    |
          | - image/table state   |
          +-----------+-----------+
                      |
                      v
               Installed Fiji
```

### 5.1 MCP coordinator

The coordinator owns the public stdio stream. Before initializing Java, the spawned worker redirects its operating-system stdout/stderr and Java `System.out`/`System.err` away from inherited coordinator descriptors into a private capture channel that is continuously drained into a fixed-size ring/drop sink. Overflow drops oldest output and increments a dropped-byte counter; it never applies backpressure to Fiji. Worker output is never forwarded directly to coordinator stdout or stderr. Only coordinator-generated, sanitized logs go to stderr under the deny-by-default redaction policy in section 8.4. A verbose-worker stress test must prove the channel cannot deadlock the JVM.

The coordinator is responsible for:

- Registering the exact MCP tool set for the selected safety profile.
- Validating request schemas, command identities, bounds, and approved paths before dispatch.
- Serializing all worker operations through one queue.
- Assigning operation IDs and maintaining bounded operation history.
- Enforcing operation deadlines and MCP cancellation.
- Terminating and replacing an unhealthy worker.
- Returning stable structured successes and errors.

### 5.2 Fiji worker

The worker is the only process that initializes PyImageJ and the JVM. It owns all Java objects, open images, Results tables, command adapters, and the catalog cache. Java objects never cross the process boundary; IPC messages contain only versioned JSON-compatible values and bounded binary payload descriptors.

The process must use a spawn-compatible startup model on every supported operating system. It must not fork an initialized JVM. The private worker protocol is not a network API and opens no listening TCP port. IPC frames, request depth, collection sizes, binary payloads, queue length, and temporary descriptors are bounded according to section 7.8. Temporary payloads are owner-only and are deleted on success, worker failure, coordinator shutdown, and next-start cleanup.

On `serve`, the coordinator begins one worker-start attempt on its lifecycle task while keeping MCP initialize, tools/list, and passive status available. A Fiji-dependent request waits for that current attempt up to the startup deadline. After a failed attempt, only a new caller-requested Fiji-dependent tool may trigger one further attempt; status never does so.

Headless is the only v0.2 execution mode. `auto`, `smart`, and direct GUI modes are removed. GUI/AWT-only commands remain discoverable with `conditional` eligibility and reason `gui_required`, but cannot be executed by this release. `capture_image` renders the selected image data without reading a desktop or GUI window.

### 5.3 Serialization and exactly-once dispatch

Fiji has global state, including an active image and global Results table behavior. The coordinator therefore permits only one worker operation at a time.

Each accepted mutating request is dispatched at most once. A timeout, cancellation, broken pipe, or unknown worker outcome is never automatically retried. Retry authorization is not inferred from MCP `readOnlyHint`: only stateless catalog reads are allowlisted for one retry after recovery; passive coordinator status needs no worker retry. Image, table, capture, and other generation-bound reads are never retried after a reset because their objects no longer exist. A successful stateless retry reports `session_reset: true` and the new generation.

Serialization guarantees that MCP requests enter Fiji one at a time. It cannot stop an arbitrary installed plugin from starting background Java threads and returning early. A command known to be GUI-event-driven or asynchronous is conditional and ineligible for standard execution unless its adapter has a tested completion contract. For other installed code, “operation complete” means that the invoked Fiji API returned; `effects_completeness` discloses whether declared outputs and observed global changes are complete, reconciled, best-effort, or unknown.

### 5.4 Timeouts, cancellation, and recovery

Requests move through `QUEUED`, `RUNNING`, and one terminal state. The queue is bounded. A queue deadline or cancellation before dispatch removes the request without touching the worker and returns a definite not-executed outcome.

When a running operation exceeds its execution deadline or receives cancellation:

1. The coordinator marks a mutating outcome as unknown because execution may have begun.
2. It closes the operation channel and requests termination of the worker's dedicated process group on POSIX or kill-on-close Job Object on Windows, without waiting for the busy JVM thread to cooperate.
3. After a two-second grace period it force-kills any surviving contained processes, then joins/reaps the worker and cleans private descriptors within five seconds.
4. It starts one replacement worker under the configured startup deadline and increments the worker generation.
5. All image, table, and opaque object IDs from the prior generation become stale.
6. The MCP stdio connection remains alive and returns a structured recovery result with `session_reset: true`.

If replacement startup fails, the coordinator stays alive in a degraded state and returns `WORKER_RESTART_FAILED`. `get_fiji_status` only reports that state. The next caller-requested tool that actually needs Fiji may attempt one new startup; there is no hidden restart loop.

The system does not claim rollback. An external file or service modified by a plugin before termination may remain modified. Process-group/Job containment is best-effort: a plugin that deliberately detaches a descendant or contacts an external service may continue work after worker death. Timeout/cancellation results therefore preserve `outcome: unknown`, explain this limitation, and the recovery demo proves both contained-child termination and honest detached-child reporting.

## 6. Capability and session model

### 6.1 Stable command identities

Display names are not identities because Fiji can contain duplicate labels and duplicate class registrations. Catalog adapters enumerate four authoritative sources independently:

- SciJava `CommandInfo` registrations.
- SciJava Ops metadata.
- Installed SciJava menu/script modules.
- The ImageJ1 menu/plugin registry, including registered class, argument, and menu path.

Every registration is preserved unless its complete canonical registration tuple is byte-for-byte identical to another entry. The public `command_id` contains the kind plus a deterministic digest of that tuple, so classes registered under different labels, arguments, priorities, or menu paths cannot collide. Deterministic suffixing resolves the theoretically possible digest collision and is tested. The catalog fingerprint is SHA-256 over the resolved Fiji identity plus the sorted, length-delimited canonical tuples; iteration order cannot change it.

If Fiji exposes insufficient identity metadata, the entry receives an installation-scoped derived ID and `identity_stability: installation`. `describe_command` must disclose this instead of pretending that the ID is portable.

Search results include both `command_id` and `catalog_fingerprint`. `describe_command`, `run_command`, and `run_plugin` require both values. A mismatched or superseded fingerprint returns `CATALOG_CHANGED`, prompting the agent to search and describe again.

### 6.2 Command metadata

`describe_command` returns all metadata available from Fiji in a normalized schema:

- ID, display title, command kind, class, menu path, source/update site when available.
- Inputs and outputs with names, roles, Java types, normalized MCP types, required/default values, choices, numeric bounds, and descriptions.
- Whether metadata is complete enough for typed execution and which registered value converters are required.
- Headless, GUI, hardware, external-service, and input-data requirements when detectable.
- Execution eligibility—`standard`, `trusted_only`, `conditional`, or `unsupported`—and machine-readable reasons.
- Catalog and Fiji fingerprints.

Unknown values are represented explicitly as `null` or `unknown`; they are not guessed. Unknown prerequisite, headless, asynchronous, or converter status fails closed to `conditional` or `unsupported`, never `standard`.

### 6.3 Session object identities and reconciliation

Every opened or declared output image receives an opaque ID tied to the worker generation. Results tables are copied into immutable, revisioned snapshots and receive table IDs. Other non-JSON Java outputs receive opaque object IDs with their Java type and a bounded safe summary; they can be passed only to a later command input whose declared type is compatible. Tool responses distinguish declared outputs from objects found through pre/post registry reconciliation.

Mutating tools require explicit image IDs whenever more than one image could be selected. A legacy command that operates on Fiji's active image must receive an `image_id`; the worker activates that image immediately before dispatch while the serialized operation lock is held. Trusted macro/script requests use the same `active_image_id` rule. An omitted ID is accepted only when the operation has no active-image behavior or exactly one eligible image exists. Otherwise the tool returns `IMAGE_ID_REQUIRED`.

Image dirty state is `clean`, `dirty`, or `unknown`; it is never invented when a Fiji representation lacks a reliable flag. Every execution response reports `effects_completeness` as `declared`, `reconciled`, `best_effort`, or `unknown`. Arbitrary installed or trusted code may mutate objects outside observable registries, so the server does not promise exhaustive affected-object reporting.

After worker replacement, any old image, table, or object ID returns `STALE_SESSION_OBJECT` and tells the agent to reopen or recreate the data. IDs are not persisted between MCP server sessions.

Session retention is bounded. Images are never silently evicted because they may contain unsaved work: creating or opening another image beyond the count or estimated-byte quota returns `SESSION_QUOTA_EXCEEDED` and tells the agent which image IDs it can save or close. Immutable table snapshots and opaque objects are evictable least-recently-used handles because no separate release tool is exposed; access refreshes their age, active operations pin them, and an evicted ID returns `SESSION_OBJECT_EVICTED`. Every returned table/object describes its retention class. Oversize single snapshots are rejected before registration. Quotas and current use are returned by status and tested under sustained sessions.

### 6.4 Bounded data

Search results, table rows, operation history, text outputs, warnings, stack metadata, and captured image dimensions all have explicit limits. Paginated tools return a continuation cursor or offset metadata. Requests above a limit fail with the allowed maximum instead of silently truncating the request. The type/capability matrix is generated from the converter registry and requires positive, negative, serialization, and real-Fiji evidence for every retained boolean/numeric/string, enum, path/file, color/axis/calibration, image, table, ROI/overlay, collection/map, and opaque-object adapter. An unregistered Java type is reported as `UNSUPPORTED_TYPE`; it is never stringified and treated as a valid typed value.

Binary image pixels are returned only by `capture_image` as native MCP image content. Other tools return structured metadata and stable IDs, not base64 embedded in JSON.

### 6.5 Finite capability taxonomy

The release manifest uses a closed taxonomy so “every supported capability family” is measurable:

1. Catalog enumeration, identity, search, and metadata normalization.
2. Scalar/enum/no-input SciJava commands and Ops.
3. Typed path and file inputs/outputs.
4. Grayscale 2D image-to-image processing.
5. RGB and multichannel processing.
6. 16-bit, stack, and hyperstack processing.
7. ROI, overlay, and opaque-object chaining.
8. Segmentation, measurement, and table production.
9. Legacy active-image plugins and global-table reconciliation.
10. Installed script modules with typed inputs.
11. Image open/save/reopen, rendering, and lifecycle.
12. Trusted macro and installed-language source execution.
13. GUI/asynchronous, hardware, external-service, and special-input conditional boundaries.

Every catalog entry is assigned one or more families from authoritative metadata and converter types, or receives an explicit `unclassified` reason. Every executable family requires a representative real-Fiji demo and converter evidence. Every conditional family requires a negative boundary test that proves it is reported rather than falsely executed or verified. An `unclassified` entry blocks the full-catalog release gate until classification is fixed or the entry is described explicitly as unsupported.

## 7. MCP tool contract

The **standard** profile exposes exactly 13 tools. The **trusted** profile exposes those 13 plus two raw-code tools. Tool-list snapshot tests fail if a stale or accidental tool is registered.

### 7.1 Status and discovery

#### `get_fiji_status`

Returns server version, safety profile, passive worker state and generation, resolved Fiji/Java/PyImageJ versions when known, mode, catalog fingerprint and counts when loaded, supported script languages, approved data roots, quotas/current use, dropped worker-output count, open-object summaries, and degraded or conditional capabilities. It never starts or restarts the worker and performs no mutation.

#### `search_commands`

Searches the complete installed catalog by text and optional filters such as command kind, menu path, headless compatibility, and standard-profile eligibility. It is paginated, deterministic for a catalog fingerprint, and returns IDs plus concise eligibility metadata.

#### `describe_command`

Describes one exact `command_id` under its required `catalog_fingerprint` using the metadata contract in section 6.2. It never executes the command.

### 7.2 Generic execution

#### `run_command`

Runs a described SciJava command, SciJava Op, or installed script module by exact `command_id` plus `catalog_fingerprint`. Inputs are a JSON object validated against normalized command metadata and the registered converter matrix. Image, table, and opaque-object inputs use session IDs and are converted to Java objects only inside the worker. Outputs are normalized scalars/collections, image IDs, immutable table IDs, typed opaque-object IDs, or an explicit unsupported-output record. The response separates declared outputs from reconciled side effects and includes `effects_completeness`.

#### `run_plugin`

Runs a described ImageJ1/legacy registration by exact `command_id` plus `catalog_fingerprint`. The adapter invokes the registered class/argument directly or uses ImageJ1's option context; it never constructs and executes macro source. In standard mode, the server generates a canonical ImageJ1 option string only from option fields disclosed by `describe_command`. In trusted mode, the same tool may accept an explicit bounded `raw_options` string for a plugin whose exact-ID adapter is runnable but lacks typed option metadata. Dialog-only, asynchronous, or GUI-required plugins remain conditional in the headless v0.2 runtime. The response uses pre/post image and Results-table reconciliation with an honest `effects_completeness` value.

### 7.3 Trusted execution

These tools are not registered in the standard profile.

#### `run_macro`

Runs ImageJ macro language source under a size and time bound. The caller must provide the code and, whenever more than one image is open, an `active_image_id` regardless of whether the source appears to use active-image behavior. Responses contain returned values, best-effort affected IDs, warnings, `effects_completeness`, and a SHA-256 code hash; operation history never stores the full source.

#### `run_script`

Runs source in an installed SciJava scripting language selected from the languages reported by `get_fiji_status`. Scalars and compatible session-object IDs may be supplied through typed bindings, and `active_image_id` follows the same ambiguity rule as macros. Unsupported languages are rejected before dispatch. The same size, path, timeout, redaction, effects-completeness, and code-hash rules as `run_macro` apply.

### 7.4 Image lifecycle and inspection

#### `open_image`

Opens a file under an approved data root and registers the resulting image. It returns an image ID, dimensions, axes, pixel type, calibration, source path, and relevant metadata. It does not display a window in headless mode.

#### `save_image`

Saves one explicit image ID to an approved path. The format follows the path/explicit format contract. Existing files require `overwrite: true`. The response includes the resolved path, byte size, format, and a content checksum so demos can verify the artifact.

#### `close_image`

Closes one explicit image ID. When dirty state is `dirty` or `unknown`, the default `discard_changes: false` refuses to close; the caller must save first or explicitly set `discard_changes: true`. Closing all images requires individual calls; no hidden “close everything” behavior is provided.

#### `list_images`

Returns bounded summaries of all images in the current worker generation, including IDs, titles, dimensions, pixel types, source paths when safe to expose, dirty state, and active state.

#### `get_image_info`

Returns detailed metadata and independently calculated basic statistics for one image ID without changing the image. Statistics disclose the plane, channel, slice, frame, ROI, sampling, and NaN policy used.

#### `capture_image`

Renders one explicit image ID, or the only eligible open image, as native MCP image content plus structured metadata. The caller chooses PNG or JPEG; the returned MIME type and bytes must agree. PNG is the default for scientific images. Dimension and quality bounds are enforced. Full-screen, arbitrary-window, and desktop capture are not supported.

### 7.5 Results and audit history

#### `get_results_table`

Returns a bounded page from an explicit table ID produced by an execution response. If the ID is omitted, it succeeds only when exactly one eligible table exists. Column names, row offsets, total row count, numeric/null encoding, and source operation ID are preserved.

#### `get_operation_history`

Returns a bounded, paginated audit history for the current coordinator session. Entries are built from an allowlist: operation ID, tool, timestamps, outcome, worker generation, parameter names/types/counts, approved object IDs, code hashes, stable error codes, and recovery events. Arbitrary string values, raw paths, scripts, credentials, image pixels, worker output, and third-party exception text are never persisted. History-query operations are not appended to the history they read, preventing self-referential pagination and preserving the tool's idempotent contract.

### 7.6 Common result and error shape

Every successful tool returns structured content with:

- `ok: true`
- `operation_id`
- `worker_generation`
- `duration_ms`
- `session_reset`
- `warnings`
- tool-specific `data`

`operation_id` is a UUID string, `worker_generation` is a nonnegative integer or `null` before a worker exists, `duration_ms` is nonnegative, `session_reset` is boolean, and `warnings` is a bounded list of stable code/message objects.

Every tool failure is an MCP error result with structured content containing:

- `ok: false`
- stable `code`
- concise plain-language `message`
- actionable `remediation`
- `retryable`
- `session_reset`
- `worker_generation`
- `operation_id` when dispatch began
- safe `details`

Error `operation_id` and `worker_generation` are nullable when failure occurred before dispatch/startup. `retryable` and `session_reset` are always booleans.

The initial stable codes are `CONFIG_INVALID`, `PROFILE_REQUIRED`, `VALIDATION_FAILED`, `PATH_FORBIDDEN`, `FILE_EXISTS`, `CATALOG_CHANGED`, `COMMAND_NOT_FOUND`, `COMMAND_CONDITIONAL`, `COMMAND_UNSUPPORTED`, `UNSUPPORTED_TYPE`, `IMAGE_NOT_FOUND`, `IMAGE_ID_REQUIRED`, `TABLE_NOT_FOUND`, `TABLE_ID_REQUIRED`, `OBJECT_NOT_FOUND`, `OBJECT_TYPE_MISMATCH`, `STALE_SESSION_OBJECT`, `SESSION_OBJECT_EVICTED`, `SESSION_QUOTA_EXCEEDED`, `UNSAVED_CHANGES`, `FIJI_STARTUP_FAILED`, `COMMAND_FAILED`, `QUEUE_FULL`, `QUEUE_TIMED_OUT`, `OPERATION_TIMED_OUT`, `OPERATION_CANCELLED`, `WORKER_CRASHED`, `WORKER_RESTART_FAILED`, `OUTPUT_TOO_LARGE`, `PROTOCOL_ERROR`, and `INTERNAL_ERROR`. Tests assert codes and fields, not fragile full prose. Validation failures before dispatch use `operation_id: null`; unknown mutating outcomes explicitly say so in safe details.

### 7.7 MCP annotations

Annotations are conservative and part of the tested contract:

- Status, discovery, list/info, capture, table reading, and history are read-only and idempotent.
- Opening an image mutates session state but is not marked destructive.
- Saving and closing are mutating and potentially destructive.
- Command, plugin, macro, and script execution are mutating and potentially destructive.
- Generic installed-code execution and trusted raw-code execution use `openWorldHint: true` because installed code can interact with resources outside the server's direct control.
- All other tools use `openWorldHint: false`.

The normative matrix is:

| `get_fiji_status` | true | false | true | false |
| `search_commands` | true | false | true | false |
| `describe_command` | true | false | true | false |
| `run_command` | false | true | false | true |
| `run_plugin` | false | true | false | true |
| `run_macro` | false | true | false | true |
| `run_script` | false | true | false | true |
| `open_image` | false | false | false | false |
| `save_image` | false | true | false | false |
| `close_image` | false | true | false | false |
| `list_images` | true | false | true | false |
| `get_image_info` | true | false | true | false |

The dynamic `parameters`, `bindings`, and typed plugin `options` objects are validated against the exact schema returned by `describe_command`. | Captured image pixel count | 4,194,304 | 16,777,216 |
| Encoded image payload | 16 MiB | 32 MiB |
| Retained images | 32 | 128 |
| Estimated retained image bytes | 2 GiB | 8 GiB |
| Retained immutable tables | 32 | 128 |
| Cells per retained table | 1,000,000 | 10,000,000 |
| Total retained table bytes | 64 MiB | 256 MiB |
| Retained opaque objects | 64 | 256 |
| Unknown-size opaque-object accounting unit | 64 MiB | 64 MiB |
| Total accounted opaque-object bytes | 512 MiB | 2 GiB |
| Operation-history entries | 1,000 | 10,000 |

Cursor tokens bind to a catalog fingerprint or coordinator session and expire when that source changes. Limits and the exact contract version are returned by `get_fiji_status`.

## 8. Safety model

### 8.1 Standard profile

Standard is the default. It enables typed installed commands/plugins and image operations but does not register `run_macro` or `run_script`.

The coordinator validates declared path-like inputs and outputs against approved data roots, blocks output overwrite without explicit consent, rejects catalog entries that cannot be represented safely enough for typed execution, and records operations. “Standard eligible” proves only that the MCP request has a complete typed adapter and known runtime prerequisites. It does **not** prove that installed Java code is benign, scientifically correct for the user's data, or confined to approved folders. Installed commands run with the user's account permissions in both profiles and may access files, networks, subprocesses, hardware, or services outside declared parameters.

Side effects default to `unknown` unless authoritative metadata or a tested adapter says otherwise. Command/plugin tools remain conservatively annotated destructive and open-world. The canonical guidance requires the agent to describe these risks and obtain confirmation when the user's request did not already clearly authorize the side effect. Command discovery remains complete even when execution is restricted, so the agent can explain why an entry is conditional, unsupported, or trusted-only.

### 8.2 Trusted profile

Trusted is an explicit setup choice and is visibly reported by status. It adds raw macro and installed SciJava script execution. Size, timeout, path checks on declared paths, redaction, serialization, and audit history remain enabled.

Trusted mode is not an operating-system sandbox. Fiji plugins, macros, and scripts run with the user's local account permissions and may access resources the MCP layer cannot detect. Documentation and setup must say this plainly.

### 8.3 Filesystem boundary

Setup requires one or more approved data roots before file I/O is enabled. Paths are expanded, resolved, and checked after symlink resolution. Inputs must exist and outputs must have an approved parent. The policy applies to MCP path fields and path-like typed command parameters.

No claim is made that data-root checks contain behavior hidden inside installed plugin code or raw source. Users needing stronger containment must run the whole MCP server in an OS-level sandbox or container; that is deployment guidance, not a v0.2 feature.

### 8.4 Logging and redaction

Logging and operation history are deny-by-default. The coordinator records only server-owned fields and allowlisted scalar summaries. It records a string parameter's name, type, length, and optional hash—not its arbitrary value. Paths are represented by an approved-root alias plus relative-path hash unless the user explicitly requests diagnostic path output. Third-party exception text and worker stdout/stderr are normalized to stable codes, sanitized, truncated in memory, and never persisted. Debug mode may increase server-owned diagnostics but does not disable source, credential, or worker-output redaction.

## 9. Setup, diagnostics, and client adapters

The package exposes one command, `fiji-mcp`, with these subcommands:

- `fiji-mcp setup`
- `fiji-mcp doctor`
- `fiji-mcp status`
- `fiji-mcp remove`
- `fiji-mcp serve`

The old `fiji-mcp-install` and `fiji-mcp-server` command names are removed without aliases.

### 9.1 Owned configuration and durable runtime

Fiji MCP owns one versioned `config.toml` and an installation manifest. For owned files the manifest stores path and content hash. For entries merged into a user-owned JSON/TOML file it stores the containing path, exact key path, and normalized installed-value hash:

- macOS: `~/Library/Application Support/fiji-mcp/`
- Windows: `%LOCALAPPDATA%\fiji-mcp\`
- Linux: `${XDG_CONFIG_HOME:-~/.config}/fiji-mcp/` for configuration and `${XDG_DATA_HOME:-~/.local/share}/fiji-mcp/` for the managed runtime

The config schema records its version, immutable Fiji MCP Git revision, validated Fiji root, approved data roots, `standard` or `trusted` profile, headless mode, timeouts/limits, and selected client adapters. It stores no credentials. Files are owner-readable/writable only where the platform supports permissions.

The `uvx` command is a bootstrap, not the long-term client launcher. After preview and confirmation, setup creates a versioned managed Python environment from the exact GitHub tag or commit and the repository's platform lock data, verifies artifact and dependency hashes, and records resolved versions. It then writes each client an absolute command equivalent to:

```text
<managed-runtime>/fiji-mcp serve --config <owned-config.toml>
```

The server therefore starts offline after initial provisioning and does not depend on a shell PATH or an ephemeral `uvx` environment. Re-running setup for a different revision creates and verifies a new versioned runtime, atomically switches config entries, and retains the old runtime until the new doctor check passes. The documented prerequisite is an installed `uv`; official OS-specific prerequisite instructions appear immediately above the single Fiji MCP setup command and are not represented as something Fiji MCP can silently provide.

### 9.2 `setup`

Setup must:

1. Detect likely Fiji roots and validate `jars/`, `plugins/`, and a usable Java/PyImageJ startup path.
2. Detect supported installed AI clients and permit explicit selection.
3. Ask for approved data folders and standard or trusted profile, with standard recommended.
4. Show the exact files and entries it proposes to change.
5. Parse and validate existing JSON or TOML before modification.
6. Create timestamped backups and write through a same-directory temporary file plus atomic replace.
7. Preserve unrelated client configuration keys and entries.
8. Install the canonical skill only where that client supports skills.
9. Provision the durable, immutable managed runtime described above.
10. Run `doctor` against the generated server command and report the result in plain language.

`--dry-run` performs detection, validation, and preview without writing. Non-interactive flags exist for automated tests, but the default experience is guided.

### 9.3 `doctor`

Doctor validates, in order:

- Python package and executable resolution.
- Fiji root structure.
- Java and PyImageJ initialization in a disposable worker.
- Catalog loading and a harmless built-in status operation.
- Approved-folder read/write probes using temporary files.
- Selected safety profile and tool-list contract.
- Generated client configuration syntax and expected location.
- A real stdio MCP initialize, tools/list, and status call through the generated command.

The default output is human-readable with one remediation per failure. `--json` produces a stable machine-readable report for tests and support.

### 9.4 `status`, `remove`, and `serve`

- `status` inspects installation and client configuration without starting a persistent MCP session.
- `remove` previews and removes only entries/files recorded in the installation manifest. It removes a skill/generated file or shared-config entry only when its current content/value hash still matches the installed hash; a user-modified file or MCP entry is retained and reported unless the user explicitly confirms forced removal. It preserves unrelated configuration and existing backups.
- `serve` starts the local stdio MCP coordinator. It never starts HTTP or opens a listening port.

### 9.5 Client order and support rule

Implementation and live acceptance proceed in this order:

1. Codex CLI/Desktop alone.
2. ChatGPT Desktop.
3. Claude Desktop and Claude Code.
4. Cursor.
5. GitHub Copilot in VS Code.
6. Additional local clients only after the required clients pass.

Each adapter owns only path detection, config parsing/merging, server-entry generation, and optional skill placement. Core MCP behavior is identical across clients.

The non-vacuous v0.2 target matrix is:

- Core CLI, stdio MCP, worker recovery, and real Fiji: Python 3.10–3.12 on macOS 14+ (arm64 and x86_64 evidence), Windows 11/Server 2022+ x86_64, and Ubuntu 24.04 LTS x86_64. CI pins versioned runner images rather than `*-latest` and records their image revisions.
- Client config-generation fixtures: every official macOS, Windows, and Linux path/format for each target client where that client is officially available.
- Live clients: Codex, ChatGPT Desktop, Claude Desktop/Code, Cursor, and Copilot in VS Code must each connect and complete the shared acceptance suite on at least one officially supported operating system. Codex runs first in the maintainer's macOS environment. Active documentation lists only the exact client/OS combinations actually verified; it does not generalize a successful macOS run into an untested Windows or Linux claim.

A client/OS combination is listed as verified only after:

- Its official config format and platform paths are covered by fixture tests.
- Setup writes and removes the entry atomically without damaging unrelated settings.
- Doctor launches the exact generated command and completes a real MCP/Fiji handshake.
- The actual client has connected and completed the required shared demos on that operating system, with the evidence in section 13 recorded.

If one of these cannot be demonstrated, the adapter is deferred and removed from active documentation rather than shipped with an unverified claim.

## 10. Canonical agent guidance

There is one maintained source of agent guidance. Client packages may add mechanically generated front matter or placement metadata, but they may not contain independently edited copies.

The guidance teaches this workflow:

1. Check Fiji status and capabilities.
2. Search by the user's scientific intent.
3. Describe the exact command and inspect requirements.
4. Open or select explicit image IDs.
5. Execute with typed parameters under the current safety profile.
6. Verify pixels, statistics, dimensions, tables, metadata, or saved artifacts appropriate to the task.
7. Report conditional limitations and do not infer scientific correctness from a screenshot.

It also teaches agents to avoid full-screen capture, avoid unrequested package installation, never place raw script content in logs, and request trusted mode only when a typed installed command cannot do the work.

Tool descriptions remain sufficient for agents that do not support skills. Automated drift tests fail if guidance mentions removed tools, parameters, profiles, or commands.

## 11. Demo-driven verification design

### 11.1 Demos are executable acceptance contracts

The user-facing demos are the primary acceptance suite, not decorative screenshots or ad hoc maintainer scripts. Every retained tool and every advertised user capability must appear in at least one executable demo.

One machine-readable manifest maps:

- Feature ID and user-facing claim.
- Required profile and prerequisites.
- Input fixture and exact prompt or scripted request.
- MCP/CLI features that must be exercised, tools allowed to satisfy the task, and tools actually observed in each run.
- Converter and capability families covered by the task.
- Expected structured outputs and scientific oracle.
- Positive, negative, and recovery test IDs.
- Real-Fiji, MCP-stdio, Codex, and client evidence.

A verifier fails when an advertised feature has no demo, a registered tool is not actually exercised by at least one deterministic demo, a retained converter/capability family lacks its required positive/negative/serialization/real-Fiji evidence, a referenced test does not exist, or guidance names a removed capability. Agent workflows remain outcome-based: observed calls prove surface coverage across the suite but do not require every model run to use one brittle exact sequence.

Independently of multi-step demos, every registered tool must have its own positive, negative, boundary, strict-input-schema, output-schema, annotation, serialization, stdio-MCP, and error-shape checks, plus a real-Fiji check wherever the tool touches Fiji. CLI commands and client adapters receive the equivalent success, refusal, rollback/atomicity, and malformed-existing-config coverage.

### 11.2 Required demo set

The curated v0.2 demo suite contains these deterministic user stories:

1. **Complete setup lifecycle:** from a clean home, dry-run setup, provision a managed runtime, configure every adapter fixture, run doctor/status/serve, preserve unrelated settings and backups, remove Fiji MCP, refuse to delete a user-modified skill, reinstall, and recover atomically from a simulated failed write.
2. **Discover and describe:** find an installed Gaussian blur command by intent, select its exact ID, and validate its typed parameters and eligibility.
3. **Image round trip:** open an 8-bit gradient, inspect it, save it, reopen it, and compare shape, pixel type, calibration, and pixel checksum.
4. **Quantitative blur:** apply a known blur to a synthetic impulse/checker fixture and compare output pixels and conserved intensity against an independent analytical/NumPy oracle within declared tolerances; a validated golden may supplement the oracle.
5. **Threshold and measurement:** segment deterministic geometric objects and verify object count, area, centroid, and Results table values.
6. **RGB processing:** run a channel-aware operation and verify channel ordering, dimensions, and independently calculated channel statistics.
7. **16-bit stack processing:** execute a max-intensity projection over a deterministic stack and verify output pixels, bit depth, axes, and calibration.
8. **Legacy plugin:** run one built-in ImageJ1 plugin through `run_plugin` and verify the actual pixel or table result.
9. **Session-object lifecycle:** manage multiple image/table/opaque IDs, resolve active-image ambiguity, refuse silent image eviction, exercise table/object LRU eviction and quotas, close one image, and verify stale-ID behavior after worker replacement.
10. **Results pagination and history:** retrieve a multirow table in pages and verify its source operation and redacted audit entry.
11. **MCP image capture:** decode returned PNG and JPEG content, verify MIME/bytes agreement, bounds, and correspondence to the selected image; prove desktop capture is unavailable.
12. **Standard safety:** prove `run_macro` and `run_script` are absent from standard `tools/list` while status/guidance explains how to opt in; reject out-of-root paths, implicit overwrite, incomplete/conditional commands, raw plugin options, and ambiguous image selection with stable remediations.
13. **Trusted automation:** opt in, run a bounded macro and an installed SciJava script, verify their scientific effects, and verify only code hashes enter history.
14. **Timeout and recovery:** interrupt a deterministic long-running worker operation, prove it was not retried, prove a contained child process is terminated, report a deliberately detached-child outcome as unknown, observe stale prior IDs, and complete passive status plus a new image operation on the replacement worker through the same MCP connection.
15. **Plain-language analysis:** have Codex discover, execute, measure, verify, save, and reopen a multi-step microscopy example without being told exact tool calls.

Existing useful demo inputs may be retained only after they receive provenance, a deterministic expected result, and a manifest entry. Unlabeled, redundant, generated, or scientifically unverifiable demo assets and scripts are removed.

### 11.3 Scientific oracles

Tests validate outcomes rather than “no exception” or screenshot similarity. Depending on the operation, an oracle checks:

- Exact arrays or independently calculated arrays within declared absolute/relative tolerances.
- Dimensions, axes, pixel type, bit depth, calibration, and metadata.
- Histogram, min/max, mean, variance, checksum, or conservation invariants.
- ROI/object count, area, centroid, perimeter, and other known geometric measurements.
- Exact Results table schema, values, null handling, row count, and pagination.
- Saved file bytes/format plus reopen-and-recompare behavior.

Scientific acceptance requires an analytical fixture, an independent NumPy/reference implementation, or an externally validated expected result. A golden generated only by the same Fiji command under test proves regression stability and may supplement—but never replace—an independent correctness oracle. Golden files include their independent provenance, generator, Fiji version when applicable, command identity, parameters, and checksum. A golden output cannot be silently regenerated as part of the test that consumes it.

## 12. Standard test layers

Demo acceptance is supported by standard software-testing layers:

### 12.1 Unit tests

Every coordinator policy, schema validator, catalog normalizer, path check, pagination rule, adapter merge, error mapper, ID rule, redactor, annotation, and CLI branch receives positive, boundary, and negative tests without a JVM where practical.

### 12.2 Worker component tests

A fake worker verifies protocol framing, serialization, timeout, cancellation, crash, malformed response, startup failure, generation changes, exactly-once dispatch, and the stateless catalog-read retry allowlist. Real-worker tests verify the same contract against PyImageJ/Fiji where applicable.

### 12.3 MCP contract tests

A subprocess client uses the real stdio transport to verify initialize, exact tool lists for both profiles, input/output JSON schemas, MCP annotations, structured errors, image content, cancellation, and continued connection after worker replacement. Importing handlers directly is not sufficient evidence for this layer.

### 12.4 Real Fiji integration tests

The release suite initializes a pinned reference Fiji distribution and the maintainer's representative installed Fiji. For each catalog source named in section 6.1, a raw registry probe collects the authoritative registration tuples independently of the MCP pagination/normalization path. The suite compares those raw sets with all MCP pages, asserting count equality, identity uniqueness, deterministic deduplication, pagination closure, fingerprint stability, and a successful description for every entry. Missing metadata is represented inside a successful minimal description with explicit unsupported/conditional reasons; a normalization failure blocks release. It then executes every required demo and converter/capability family and records conditional entries with machine-readable reasons. No release claim is based solely on mocks or on the adapter checking its own output.

### 12.5 Regression tests

Every defect discovered during implementation receives a focused test that fails before the fix and passes after it. Bugs are reported to the user as they are found. A retained feature with an unresolved correctness defect blocks release; if a reliable fix and test are not possible, the feature is removed.

### 12.6 Coverage gates

- Production-code aggregate: at least **90% line coverage** and **85% branch coverage**.
- Every production module: at least **80% line coverage** and **75% branch coverage** when the metric applies.
- Safety policy, worker lifecycle/IPC, execution routing, and config mutation modules: at least **95% line coverage** and **90% branch coverage**.
- Exclusions are limited to type-checking guards, platform-impossible defensive markers, and generated version metadata. Every exclusion requires an inline reason and review.

Coverage is a gap detector, not proof of scientific correctness; the demo oracles remain mandatory.

### 12.7 Static, security, and artifact gates

The release gate requires all of the following with zero actionable findings:

- Ruff lint and format check.
- Mypy across the production package with no errors.
- Bandit for first-party Python security issues.
- Dependency vulnerability audit with documented handling of any upstream advisory.
- Wheel and source distribution builds from a clean checkout.
- Package metadata validation and installation of each artifact into a clean environment.
- Exact artifact-content assertions so stale skills, demos, plugins, release files, or machine-specific configuration are not accidentally shipped.
- Secret and machine-path scan across tracked release contents.

No test required for an advertised feature may be skipped in the release run. Platform-specific tests execute in their corresponding supported-platform job rather than being counted as acceptable skips.

## 13. Codex-first and other-client acceptance

Codex is the first live agent gate. Later client validation does not begin until the complete Codex demo suite passes.

Codex receives plain-language tasks and the same public MCP surface a user receives. Assertions inspect final Fiji state and artifacts, not a brittle exact sequence of tool calls. The Codex gate covers:

- Discovery and parameter inspection.
- Quantitative command/plugin execution.
- Save/reopen verification.
- Results table interpretation.
- Clear handling of invalid input and conditional commands.
- Standard-profile restrictions.
- Trusted macro/script use after explicit opt-in.
- Timeout, worker replacement, and recovery.

After Codex passes, the same core demo workflows are exercised through ChatGPT Desktop, Claude, Cursor, and Copilot according to the support rule in section 9.5. Client-specific tests focus on configuration, discovery of the server/skill, MCP connection, media handling, and completion of the shared scientific outcomes.

Every live-agent demo runs three times from clean client conversations and clean Fiji sessions; release requires three successes out of three. A failure invalidates that task's run set until the defect is understood, fixed or removed, and all three clean runs are repeated. The release verification matrix records date, OS/architecture, client build, model/provider version when exposed, model settings, canonical-skill revision/hash, exact prompt, redacted tool transcript, clean-session identifiers, Fiji/catalog fingerprint, safety profile, demo ID, scientific oracle result, duration, and outcome. Rows cannot be filled with “assumed,” “not tested,” or a required skip.

## 14. Stale-code and repository cleanup

The implementation plan will delete rather than preserve superseded features. Expected removals include:

- The current 19-tool registration and old output schemas as they are replaced by the exact v0.2 contract.
- Batch-macro and workflow meta-tools; agents compose the smaller core tools instead.
- `list_extensions`, because current real-Fiji behavior does not provide a trustworthy extension catalog and command discovery replaces its useful role.
- Screenshot modes for full screen or arbitrary GUI windows.
- The current image-comparison metric as a scientific verifier.
- Result-text parsers and macro-template catalogs that exist only to support removed workflows.
- Duplicate bundled skills and the hand-maintained Cursor plugin bundle in favor of one canonical guidance source and tested adapters.
- Repository-local machine configuration such as `.mcp.json` if tracked.
- Stale `plan.md`, superseded demo drivers, shell installers, dead exports/state, fake timeout/retry code, generated cruft, and tests that assert removed behavior.

Cleanup applies only to tracked project content or files created by this work. Existing untracked user files—including `.agents/`, `.codex/`, `.coverage`, and `AGENTS.md` in the current workspace—are preserved.

Code is not removed merely because its filename is old; the feature manifest and dependency/search checks must first prove it has no retained consumer. Conversely, an untested feature is not kept merely because it currently works in one manual run.

The finished repository retains:

- Focused production modules with one responsibility each.
- Deterministic demo fixtures and their provenance.
- The executable demo manifest and verification harness.
- One canonical guidance source.
- Current user documentation and supported-client setup instructions.
- Historical tagged release artifacts that are not part of active v0.2 behavior.

## 15. Release gate and GitHub publication

The release proceeds through a non-circular evidence sequence:

1. Run the complete local preflight and real-Fiji/Codex gates on one immutable commit.
2. Push that commit and open a **draft** GitHub pull request so remote matrix CI can test the same SHA.
3. Associate CI artifacts and external live-client reports with that SHA without modifying source files.
4. If a fix changes the SHA, discard prior evidence and repeat from local preflight.
5. Mark the pull request ready only after local, remote, and client evidence all pass.

The pull request may become ready only when all of these statements are supported by current evidence:

1. The feature manifest covers every registered tool, CLI command, advertised client adapter, safety profile, and user-facing demo.
2. All 15 demo stories pass where their profile applies, including real Fiji and scientific oracles.
3. The full installed catalog is discoverable and describable; all unsupported/conditional entries have explicit reasons.
4. Standard exposes exactly 13 tools and trusted exposes exactly 15, with exact schemas and annotations.
5. All required unit, branch, worker, stdio MCP, real-Fiji, regression, Codex, and supported-client checks pass with no required skips.
6. Coverage, lint, format, typing, security, dependency, clean-build, install, and artifact-content gates pass.
7. Every bug found during the work has either a verified fix and regression test or caused the affected feature to be removed.
8. No known release-blocking defect remains in a retained or advertised feature.
9. Active docs and canonical guidance contain no removed names, stale setup instructions, machine-specific paths, unsupported clients, PyPI publication instruction for v0.2, or full-screen capture claim.
10. The setup flow succeeds from the immutable GitHub revision used for verification.

Preflight-passing changes are pushed on `codex/fiji-mcp-v0.2` only to obtain remote evidence through a draft pull request. After every gate passes, that same draft is promoted to a ready pull request with concise verification evidence. This project does not publish v0.2 to PyPI and does not add a release-notes document. Merge or tag actions that affect the protected default branch occur only through the repository's normal GitHub review controls.

Implementation is complete only when each requirement has direct evidence. The implementation plan must maintain this mapping:

| Requirement | Authoritative evidence |
|---|---|
| Non-coder setup | Clean-home setup/doctor acceptance transcript and config diff fixtures |
| Universal Fiji gateway | Full catalog scan report, identity/metadata checks, and representative-family executions |
| Exact MCP surface | Standard/trusted stdio tool-list and schema snapshots |
| Scientific correctness | Demo oracle reports over deterministic fixtures |
| Safe profiles | Tool visibility, path, overwrite, unsafe-command, and trusted-code tests |
| Real timeout/recovery | Worker PID/generation replacement test over one persistent MCP connection |
| Codex first | Timestamped passing Codex acceptance report preceding all other client reports |
| Other supported clients | Versioned client/OS matrix with actual connection and shared demo outcomes |

Indirect evidence—such as a narrow smoke test, a screenshot, high aggregate coverage, or the absence of a reported exception—does not prove a broader requirement.

## 17. Design influences and constraints

The design uses ideas, not wholesale architecture, from related tools reviewed during discovery:

- `royerlab/napari-mcp`: guided installer behavior, configuration backups, uninstall/dry-run ideas, registry contracts, and bounded output patterns.
- `biopb/biopb-mcp`: process isolation and worker recovery principles, simplified here to a private local pipe and a single serialized worker.
- Napari agent/plugin projects: discovery-first agent guidance and two-level capability catalogs.
- Scientific agent benchmarks: outcome-based tasks rather than exact tool-call matching.

Only permissively licensed sources may inform reusable implementation, with attribution where required. Restrictively licensed comparison projects may inform behavior-level ideas but no code is copied.

## 18. Final acceptance criteria

The design is satisfied when a person with Fiji and a supported AI client can run the guided setup without editing code, ask the agent to perform every executable demo, receive quantitatively correct results, recover from a killed Fiji worker, and understand every conditional limitation; and when the exact GitHub commit proving those outcomes passes all release gates above.

Anything advertised but not demonstrated and tested is removed before publication.
