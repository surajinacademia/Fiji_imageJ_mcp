# Fiji MCP v0.2.0 Remaining Client Adapters Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add only those ChatGPT, Claude, Cursor, and GitHub Copilot adapters that can be proven to launch the same local stdio server, preserve user configuration, consume the canonical guidance when supported, and complete shared scientific outcomes after Codex has passed.

**Architecture:** Every adapter implements the same detection/plan/verify protocol and produces ordinary `ConfigMutation` objects. Client-specific code contains no Fiji behavior. Official config formats are fixture-tested on every claimed platform; feasibility runs then validate actual clients in strict order, with Codex rerun first. Plan 05 repeats the release-grade sequence after the whole repository is frozen.

**Tech Stack:** Pydantic fixtures, JSON/TOML configuration, atomic transaction layer, managed stdio launcher, pytest, and installed desktop/CLI clients.

## Global Constraints

- Start only after Plan 03 produces a valid preliminary Codex 3/3 marker.
- The Plan 03 marker proves Codex-first sequencing but does not remain valid after source changes. After adapter implementation freezes, rerun Codex before collecting any other-client feasibility evidence.
- Use only official current client documentation and behavior as authoritative for config formats and supported transports. Record URLs, access dates, client builds, paths, and formats in `verification/client-matrix.json`.
- Do not add HTTP, remote MCP, web, mobile, bridge daemons, or a listening port to satisfy a client. If a client lacks local stdio support, remove its adapter and active support claim.
- Client adapters may detect paths, parse/merge config, generate the same absolute server entry, and place a mechanical skill copy. They do not alter tools, schemas, runtime, safety, or scientific behavior.
- Each adapter must pass absent/existing/malformed/config-conflict/dry-run/backup/rollback/removal/user-modified tests on every officially supported platform fixture.
- A fixture-only adapter is not advertised as verified. Actual-client MCP connection and shared-demo evidence are required.
- Evidence remains under `.verification-artifacts/$GIT_SHA/clients/` and is never committed.
- For every retained or explicit-unsupported adapter, run its listed focused test after writing the new case and confirm the intended failure; rerun it after implementation/removal and confirm it passes.

Required driver interface:

```python
class ClientAcceptanceDriver(Protocol):
    client_id: ClientId

    def begin(self, request: ClientRunRequest) -> ClientRunSession: ...
    def finish(
        self,
        session: ClientRunSession,
        *,
        exported_response: Path,
    ) -> ClientRunEvidence: ...
    def abort(self, session: ClientRunSession) -> None: ...
```

`ClientRunEvidence` combines client metadata and final response with server-owned redacted MCP tool traces, clean-session identifiers, filesystem/image/table artifacts, and independently computed oracle results. A manually entered “pass” flag is never evidence.
